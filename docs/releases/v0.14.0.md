# Moebius 0.14.0

Still an early prototype: use it only with throwaway repositories and with model accounts whose spending you watch.
Its contracts may change in any later release without a way to migrate.

This release lets a team plan its work in Moebius: several people with roles, projects over any number of
repositories, the organisation's wiki, and planning. The web app has a new look, and the desktop app is back, built
with Tauri around the web app. Read "Upgrading from 0.13" before you install it over a running server.

## More than one person

One server is one organisation, and its people are records of their own ([ADR 0018](../adr/0018-more-than-one-person.md)).
Each has a handle (`@lea`), a name and a role: an `owner` does everything, including the configuration, plugins,
rules, agents, secrets, repositories, projects and people; a `member` works on issues and cards, comments, edits the
wiki, plans and merges changes; a `viewer` reads, comments and writes issues and requests, which wait in the inbox as
an outside author's do. Every route of the desktop API names the role it needs. A person is disabled, never deleted,
so that what they did keeps its author.

People sign in with access tokens. An owner adds a person on the People page (or `POST /v1/people`) and hands over
their first token; a person makes more of their own on My tokens and revokes any of them, and an owner sees when each
was last used. Tokens are stored only as hashes, and Moebius stores no passwords. The web app asks for a token once and
keeps a session, which now lives in the store and survives a restart of the server; signing out, revoking the token or
disabling the person ends it. `moebius login` checks a token and saves it with the server's address in `cli.toml` for
the commands that follow.

What a person does carries their identity: a judgement records `person:<handle>`, an issue a person wrote has that
author, and column scripts see who acted. A card and an inbox item can be assigned to people, one at a time; `@handle`
in a comment mentions a person, and a person follows the cards they wrote or were given, and any other by choice. What
concerns a person is a notice in the Inbox's Mentions tab, with a read mark of their own; nobody is told of a move they
made themselves. A chat belongs to the person who started it, and others see it once it is shared. Favourites and
recently seen places are kept per person. An owner can have Moebius post its events to a URL as outgoing webhooks,
signed with HMAC-SHA256 and tried again on failure; a hook that gives up leaves an inbox item.

## Projects over any number of repositories

A project is one board with any number of repositories, or none
([ADR 0019](../adr/0019-a-project-is-a-board-over-any-repositories.md)). Each has a key, and its cards are named by it,
such as `WEB-24`; a card of a forge keeps the forge's number beside it. Every project has files of its own, a git
repository Moebius keeps for it without a forge, so a board needs no repository: a card of such a project is worked on,
reviewed and merged in the project's files like any other. A repository's new issues land in its home project, unless
a `project:<name>` label sends one to another project the repository belongs to.

Settings are split by what they are about. The workflow (the column scripts) is the project's, in `projects/<name>/` of
the harness configuration repository; what is about code (checks, test first, review notes, code rules) stays with each
repository in `repos/<name>/`. A project's settings page has tabs for both.

A card names its repositories before its run starts, and its run gets a worktree of each. The Reviewer sees every
change of the card at once, each judged by its own repository's standards and the whole judged against the issue, and
the changes are merged together in the order the card names its repositories. A merge that fails stops there and marks
the card, and a card stays out of Done while one of its changes was closed on the forge without being merged. The web
app shows and edits a card's repositories and each of its changes.

A project can be private: only its members see its board, its wiki pages, its cycles and what the Retro learns from it,
owners included unless they add themselves. Its cards and counts stay out of every list, figure and webhook of
someone who is not a member.

## The wiki

The organisation's pages are a git repository, cloned from `[wiki] url` and kept like the harness configuration
repository ([ADR 0022](../adr/0022-the-wiki-is-a-git-repository.md)): the organisation's pages at the top, a project's in
`projects/<key>/`, every edit a commit by its person, pushed at once. The Wiki page reads, edits, moves and searches
them and shows each page's history. `[[Page]]` links pages, a card's key links the card, and each page lists its
backlinks; a page that is renamed or moved keeps the links to it. Links and backlinks resolve only among the pages
the reader may see. Agents read the wiki when they work on a card and propose pages through the Inbox
(`"$MOEBIUS" wiki propose`), which a member merges or dismisses; `moebius wiki search` searches it from a terminal.
Templates for issues (per kind) and for pages are kept in the harness configuration repository.

## Planning

- **Priorities, due dates and estimates** on every card, each kept as a label so that the forge shows it. The board
  starts urgent cards first. The Moebius agent proposes an estimate from like cards, and the Retro lists the cards whose
  estimate was furthest off.
- **Milestones** are goals of the organisation with a target date and cards of any projects, shown as a list and a
  timeline. **Cycles** are time boxes of one project with a page of their own, a burn-up, and closing that carries the
  unfinished cards on.
- **Kinds of issues** (a bug, a feature) with fields of their own, defined by an owner and picked per project.
- **Duplicates and related issues**: marking a duplicate closes the issue and keeps the link, and a new issue gets a
  comment that names the open issues most like it.
- **Stale cards and the archive** are column scripts: scripts see `card.moved_at` and get `moebius.now`,
  `moebius.archive`, `moebius.hold` and `moebius.notify`.
- **Saved views**: a filter with a layout (list, board, calendar by due date, timeline by cycle) and a sort, kept for
  its person or shared with every member.
- **Analytics** of cards and points done, the time from start to done, the time in each column, tokens per point and
  the burn-up of cycles and milestones.
- **Intake** per project: a form for a request in a person's own words, which the Grilling partner drafts into an issue
  for a member to accept or decline.
- **Jira import**: a project's issues with their fields, comments, links, sprints as cycles and epics as milestones,
  run again as often as needed.

## A quiet new look

The web app is drawn to a new standard ([ADR 0020](../adr/0020-a-quiet-standard-with-depth.md)): warm greys, smaller
type, colour only on small things, and depth through surfaces instead of lines. States are status icons and grey text
instead of coloured pills, and labels a dot and a word. The board's selects are filter chips with Display, and the same
filter bar is on the Inbox, Fleet, Workflows, Rules, Usage, Decisions and Analytics. The command bar is a palette with
the commands of what is in focus first, and keyboard shortcuts have a page that lists them. The right column of a page
holds its properties, edited in place, and the Moebius agent. Settings, rules and workflows are lists with the chosen
item beside them. The sidebar has a project switcher and Plan and Automate groups; New issue is a dialog on `C`, a
card's history is one timeline, and several cards or runs can be chosen at once.

## The desktop app

The desktop app is the web app of the same release in a window of its own, built with Tauri 2
([ADR 0021](../adr/0021-a-desktop-app-in-tauri.md); [the guide](../guide/desktop-app.md)). It runs on Linux and Windows
and refuses a server of another minor version, naming the release that matches. It connects with an access token, kept
in the system's keychain, to several servers in a rail at the left, each with the count of its Inbox. It can set up and
start a server on this machine (on Linux, and on Windows inside WSL 2). It notifies natively of what the Inbox gets and
counts the unread on its icon; its tray icon shows the agents at work, the Inbox and today's tokens, and has **Pause all
agents**, which holds every run of the server until it is resumed (`moebius pause` and `moebius resume` do the same).
`Ctrl+Shift+Space` opens a small window from anywhere to ask Moebius or make an issue, and a second start of the app
brings the first forward. The app is unsigned: Windows SmartScreen warns on its first start, and the guide says how to
open it. `moebius open` and `moebius connect` stay for everyone without it.

## CI

The web app's end-to-end tests run against a real `moebius serve` again, besides the fake server. CI builds the desktop app on Linux and Windows and checks that the bundles start. A push to
a branch is built only through its pull request, and a newer push cancels the older run.

## Upgrading from 0.13

The store migrates itself when the server starts, and the change cannot be undone: back up the data directory first
([Running Moebius](../guide/running-moebius.md)). Then:

- **One project per repository.** Every repository gets a home project with its name and a key made from it, and
  every card of the repository is on it. Cards are named by that key from now on.
- **Column scripts move.** The server moves each repository's scripts from `repos/<repository>/` to
  `projects/<project>/` of the harness configuration repository in one commit when it starts. A script that lands in
  `repos/` later moves the same way.
- **`card.change` is now `card.changes`**, an array with one change per repository, and `moebius.publish_change`,
  `moebius.open_pull_request` and `moebius.run_checks` return arrays. A script of your own written for one change
  raises an error that says so, and its cards stay where they are until you loop over the array, as the default
  scripts do. Scripts see `card.repositories` too.
- **The scripts routes moved to projects.** `GET`, `PUT` and `DELETE /v1/repositories/{id}/scripts/{column}` are now
  `/v1/projects/{id}/scripts/{column}`.
- **The server's token belongs to the first owner.** It still works for scripts, but acts as that person and is
  refused while the first owner is disabled. Records from before, by the author or decider `person`, are given to the
  first owner. Give everyone else a token of their own; the training export still writes `person` without who it was.
- **Every route checks a role.** The desktop API reference names the role each route needs; a token whose person has
  a lower one is refused with `403`.
- **The desktop app and the server must share a minor version**: the app of 0.14 connects to servers of 0.14 only.
