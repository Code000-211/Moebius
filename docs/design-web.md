# Web app design standard

The standard the web app (`web/`) is built to. It supersedes [`design.md`](design.md) here: that one is the brief the
iced desktop app is built to, and the two themes are not kept in step ([ADR 0016](adr/0016-the-web-app-has-its-own-design-standard.md)). Every value below is a token in
[`web/src/styles/theme.css`](../web/src/styles/theme.css), which holds the light and dark pair of every name;
`web/src/styles/tokens.test.ts` holds the tokens to it, and `web/e2e/design/audit.test.ts` (`pnpm audit:design`)
measures every page against it in both themes at both widths.

This page governs the look, the words and the behaviour of every screen of the web app, so that the code, the tests and
the documentation can cite one thing; `web/README.md` maps the modules it is built from.

Aim for the clarity, warmth, and polish of a well-designed consumer app: thoughtful spacing, plain words, precise status, care with small details. A first-time user starts the primary task within 10 seconds. One glance answers what is happening, what matters, and whether anything needs attention.


## Principles
- One focal point per screen.
- Show outcomes, not machinery.
- Keep the person in control: preserve input, allow cancellation, keep unrelated actions usable during background work.
- Color carries meaning. Neutral foundation; strong color only where attention is warranted.
- Motion and notifications mark meaningful change only.
- Nothing should make someone feel slow, behind, or overwhelmed.

## Voice
One voice for labels, messages, errors, and generated text.

- Lead with the answer or what changed. Purpose before mechanism; cause and effect when explaining why.
- Sentence case throughout, buttons and headings included. Digits for counts: 3 items.
- Present tense for ongoing work, past tense for completed. Specific verbs: Reading, Comparing, Saving.
- A day is said as "Today", then "Yesterday", then the date itself — `27 Oct`, with the year once it leaves this one. A raw `2026-10-27` in a heading makes the reader do arithmetic to find out how recent it was.
- A gap is said one way — `just now`, `5 min ago`, `2 h ago`, `2 d ago` — from the one helper (`ui/lib/format.ts`), never as `5m ago` on one page and `5 min ago` on the next. A time of day keeps the clock that wrote it (`07:33 UTC`) beside the named day.
- A count agrees with its noun from one helper — `plural` and `noun` in `ui/lib/format.ts`. A page does not write `n === 1 ? "card" : "cards"` for a word; `noun` is for the case where the number is already on screen and only the word has to agree.
- A count of what waits for you is said even when it is nothing: Inbox 0 answers the question the page was opened to ask. A count of what the machines are doing speaks only when there is something to report, and then in a number alone, coloured where the number means work is happening: the row already names what it counts, so "Fleet 2" and never "2 live".
- A step that has finished says how long it took — `Thought 12s`, from `elapsed` in `ui/lib/format.ts` — because a step without a length looks like it is still going.
- A title already says what a page or a box is. The line under it carries the state of the thing — a count, a warning, what is missing — or is not written at all. A category is not a second heading above a title: the navigation already says where a page lives.
- On failure, say what happened and what to do next. End with an action only when there is one.
- Labels: short verbs for actions (Save, Try again), nouns for destinations (Settings, History). Prefer 2-4 words. Icon-only controls get accessible names; helper text states a consequence or constraint.
- One term per concept. Keep a glossary so names match across navigation, controls, messages, and docs.
- The same state has the same words wherever it is said: "Your turn" on a card's badge, in the dock, on a run and on the Fleet tile; "Built in" for anything Moebius brings itself — an agent, a skill, a script, a plugin. A second name for one state ("Waits for you", "In the server") makes a person learn a synonym.

Never: decorative punctuation and exclamation marks, throat clearing ("Let me", "It's worth noting"), filler praise ("Great question"), narration of internal steps ("I've gone ahead and"), hype ("seamless", "powerful", "smart"), jargon where plain words work.

| --- | --- |
| Your document has been successfully saved! | Saved. |
| Processing… | Uploading 3 files |
| An unexpected error has occurred. | Couldn't save your changes. Try again. |

| Are you sure you want to remove this item? | Item removed. Undo |

### Generated text
- Sentences of 20 words or fewer. Short replies of 1-3 sentences, under 60 words. Longer explanations go in a structured view.
- Active voice, one topic per sentence, a clear referent for every "this", "that", and "it".
- State only what was observed, checked, or provided, and name real gaps. Recommend an option, with reasons, when a decision is needed.
- Ask only for what the system cannot obtain itself. Replace a confusing explanation with a concrete example.
- Explain through the person, their action, the condition, the result: "Today, changing the filter clears your selection. Saving it separately would keep it."
- Every message stands alone, without earlier messages or outside references.

## Write to fit
- Keep titles, reasons, and action labels visible; wrap rather than truncate. Truncate only compact navigation lists whose full content is easy to open.
- A line that must stay on one line — a command, a path, a name in a bar — fades out at the end that runs short and keeps the end that identifies it: the beginning of a name, the end of a path. An ellipsis mid-word, or a hard cut, reads as broken; a fade reads as "there is more". A line that fits shows no fade, and asks for no tooltip either: the tooltip holds the whole of a line that ran out, and repeating a line that is already whole on the screen is noise in a box nobody asked for.
- A scroller says when it is cut off: the edge with more behind it fades out and an edge that shows everything does not, because a fade that lies about hidden content is worse than none. It masks the scroller rather than laying a gradient over the top, so the content fades into what is behind it instead of into a colour of its own (`ui/page/ScrollFades.tsx`, and `useScrollFades` where something else draws the scroller — the virtualised list of a conversation). A conversation needs it more than a lane does: it is read from its end, so it always has the part just left behind cut off at the top.
- A path is set in the font the list of paths is set in, and monospace is kept for what is literally typed — the line of code a search found, the body of a file. Two lists of the same paths in two typefaces read as two kinds of thing.
- Put the meaningful part of a long path or identifier in view. Size layouts for realistic content, including longer translations.
- Keep live status under 40 characters. Set length expectations wherever content is created.

- A description that is cut short stops at a whole number of lines and lets the last of them fade out, so the cut reads as a cut and not as writing that happened to end there. A compact list stops at four lines, the whole of the description one click away in the detail beside it. A board card is stricter — three lines (`ui/page/FadedClamp.tsx`) — because a column of them is scanned side by side, and it earns its fade the way a scroller does, by measuring first (`ui/lib/useBoxWatch.ts`): a description that fits the three lines is drawn plain, because a fade over writing that is all there is a lie.

## Type, color, shape
System font, or an equally readable alternative; monospace only where character precision matters. Scale: 12 caption, 13 metadata, 15 body, 17 emphasized, 22 section title, 28 page title. Body line height about 1.5. Regular and semibold for most content; heavier weights for a few headings. Tabular numbers for changing counts and timers.

- Fill primary buttons with primary text color and a contrasting label. Keep category colors distinct from status colors, and use restrained tints for categories, avatars, and diagrams.
- Pair color with text, icons, or shapes. Check contrast in both themes; muted must never make required information unreadable.
- A state that almost every row is in is a quiet mark, not a pill: a finished tool call is a gray check, so the eye lands on the rare row that failed, is blocked or waits. The same holds for an action whose usual outcome is success — asking the upstreams again ends in a gray check beside the button, because the answer that went wrong is already said in words, in red, above it. The word stays for a screen reader, and in a tooltip only where the mark stands for a state a person is weighing. The same reasoning empties a list of a repeated word: rows that are nearly all waiting print "Idle" as many times as there are rows, and the word that repeats is the one nobody reads — so the mark moves to the end of the row, the word goes, and the name of the row keeps it for whoever cannot take the colour in (`app/shell/Sidebar.tsx`).
- Follow the system theme, with an explicit override when useful.
- 8pt spacing grid. Interactive rows at least 40px tall, at the same height whether a sidebar is open or a rail, so nothing moves when the width changes. One exception, measured rather than waved through: a row of a conversation's step log — the thought, the tool call, the file an agent wrote, all of them disclosures you click — is 32px tall and its rows sit 4px apart, in the page and in the dock alike, so a log of what an agent did reads as one body of small marks rather than a list to choose from. The block that earns that height is the one `Turn.tsx` marks, and `web/e2e/design/audit.test.ts` holds a marked log to 32 and everything else to 40. Where a row reads crowded but the control inside it is the size it should be, take back the slack rather than the target: a negative margin equal to the slack keeps the 40px the hand aims at and puts the line of type one gap from its neighbours, which is what a card's title does. Neither is an excuse for a control that has not arrived yet to hold the space it will need: a control that only appears when a block is being looked at is out of the flow until it does (`copy-float`), because an invisible 32px row under every message is a band of nothing that pushes the words up, and where nothing can be hovered it stays in the flow and stays visible. Radii: 16 for cards and sheets, 12 for inputs and buttons, full for pills and avatars. Leave generous space between unrelated groups. Resolve crowding by cutting content or rearranging, not shrinking.
- A shadow marks a floating layer, and marks it once: a card inside a card, a reply inside a card, sits flat on the surface it is read against. Two elevations stacked read as two sheets of plastic, and say nothing about which one is on top. Cards are borderless; a hairline is for rules, dividers and an unfocused field. A grouped navigation list is held apart by its labels and the space around them, not by a rule under every group — a rail shows no labels, so the line would divide nothing and be the one thing that moves when the width changes. A group's label names it and goes nowhere; the way into everything the group holds is a row of the group, at the height of the rows beside it — the Projects list opens on an "All projects" row, not on the word over it. A panel that stays while a thing is selected — the inspector a card opens beside its board — is read as part of the page rather than a layer laid over it, so it runs the window's whole height flush to its three edges, keeps its corners square, and says where it begins with a hairline rather than with a radius and a shadow.

## Components
- Buttons: one clear primary action, quieter alternatives, consistent sizing. A button is as wide as its label, never the width of the row it happens to sit in. An action that starts a new thing says it with a plus, on the page header and in an empty place alike, so the same verb is drawn the same way wherever a person meets it. A destructive action is the `danger` variant wherever it appears, including the button that opens the question.
- A delete is asked once, in a dialog (`ui/page/ConfirmDelete.tsx`) that says what is removed and, for a thing that is going, that it is stopped first. Its buttons are Keep and the danger Delete; the server's refusal stays in the dialog. The Delete that opens it sits in the same place on every page: in the actions of the thing's own header or row, as the danger variant. After the delete the list updates from the event, and the page of what was deleted is left for its list.
- One thing that is on or off is one switch (`ui/page/Switch.tsx`) with the word it stands on beside it, never two buttons offering "On" and "Off": the pair reads as two actions rather than one state, says nothing at all while neither is pressed, and is twice the surface to hit. A switch says its state by the end the knob is on, then by the word beside it, then by `aria-checked` — never by the colour of its track alone.
- Inputs: clear label, visible focus, preserved content, errors beside the field. Let them grow when content needs it. A field is the lightest surface in the card — white on a white card, with its edge drawn inside the box — never the same colour as the card behind it, or the thing to type into cannot be seen.
- Tooltips supplement and never carry essential information. Toasts appear only when the current screen does not already show the result. Dialogs interrupt only for decisions that genuinely need it, and never trap. Sheets keep the underlying screen recognizable.
- A sheet ends where the last thing in it ends: nothing sits in a band of empty space under the content, and a list that scrolls reaches the sheet's own padding. So does a box beside a column that grows: a file tree held to the height of the column next to it leaves a band under its last row, which reads as a box that failed to fill, so it stops where its last row stops (`app/projects/FilesPanel.tsx`).
- Work that wants the height of the page — a shell in the clone of a repository — is a sheet over the page rather than a band under its content. The screen behind stays recognizable, and the work gets the height it needs instead of a strip that has to be scrolled inside a strip.
- A search that filters a column sits above the column it filters, not over it: a sheet opened to look for a file hides the very thing the letters are narrowing, and every search closes what it was about. The field waits for the typing to settle, so a search costs one per word and not one per letter, and a search still running keeps the hits it had, so the list does not jump to nothing between two keystrokes (`app/projects/FindPanels.tsx`). A list of what it found floats under the field rather than pushing the rows below down, because the rows below are what the search is reading against.
- A page that is a thing inside another thing — a repository inside the list of projects — carries the way back on the left of its name, which is where a hand goes looking for it. It is an icon named by a tooltip, because the room belongs to the name, and the title beside it is cut rather than wrapped so the head stays one line (`ui/page/PageHeader.tsx`). A page that is the top of its own group is not such a page: the way out of the Settings list stays a Back row under Search, at the height of every other row.
- An empty place names the next action and offers it ready-made — two or three starting points that fill the field or start the thing — rather than explaining what an empty place means.
- A navigation entry leads where a person wants to be, not to an empty field: Chat opens the most recent conversation when there is one. The entry stays standing across everything it leads to, including an address of its own. It stands on the selected fill, the one fill every chosen row in the app wears — the sidebar once had a lighter current colour of its own, and a person read the chosen page and the chosen row of its list as two different kinds of chosen. The hover of the navigation is the shared hover too: a layer of its own for a fill laid over a row says nothing the row cannot say.
- A path shows the part that names the file (`SKILL.md`), with the whole of it kept where it can be read — the tooltip, the title, the detail beside it.
- A file that is read as often as it is edited — a skill, a page of the reference — is offered drawn as well as raw (`ui/page/MarkdownBody.tsx`), and opens as the text: the text is what a person went there to look at, whether or not they can change it, and the drawing is one tab away. How it is read is held above the file, so moving along a list of them never asks for the choice again.
- A field is never blank. What stands now is written in words, including the answer that comes from the agent or the server rather than from a pick: "Server default", not an empty box that leaves the person guessing whether the page loaded. Where a field is empty because what it writes to is gone, it says so and names the way on — "Pi ended this chat. Start a new chat to continue."
- An action that leaves nothing to look at is an item of the list it belongs to rather than a page of its own — Sign out is a row of the Settings list, not a screen. The same holds for a row that only goes somewhere: the way back out of the Settings list is a Back row under Search, at the height of every other row, not an icon parked in the header.
- A control that changes the shape of the navigation sits in the navigation's head, beside the mark, in both shapes: that is where a hand goes looking for it. It was moved to the foot of the list once — to give the mark the head to itself — and a person asked for it back the same day, because at the foot it sat out of sight of the thing it changes and under a list that scrolls. The head is the same 96px open or collapsed so the rows under it keep their place; in a 56px rail the mark and the control stack inside it, and the height is what gives the mark room above it — 14px of the head is nobody's but the mark's — since a pair that fills its box reads as one thing crammed against the top edge. The connection's dot rides the mark's top corner, because a dot at the bottom of the mark lands on the control beneath.
- A field that can be left blank says what blank means — "No limit", "This one or the secret", "Set both, or neither" — in the place a blank would otherwise sit. A key with a default is said the same way ("Default 3"), so an empty field is never a guess.
- A list with nothing in it takes no column of its own: the empty state that answers it — the one holding the button that makes the first row — uses the whole width (`ui/page/List.tsx`).
- A collapsible row opens its own panel at the row's width: the box of what a tool printed starts and ends where the row it belongs to does. A list of separate items under a heading may still step in, because those are children rather than one box opening.
- A mark and the line of text beside it share that line's middle. A pill nudged down to meet the first line of a row reads as a mistake as soon as there is a second row.
- Skip unnecessary nesting, repeated containers, crowded toolbars, and long undifferentiated settings pages.

## Shared components
One implementation of each control, in one place: ``web/src/ui/``.

- Use a shared component before building a new one. When none fits, extend it with a variant rather than copying it into a feature.
- Components read color, spacing, radius, and type from named tokens (Surface, Primary text, In progress), never raw hex or one-off values.
- Consistent names across the set. Variants: primary, secondary, ghost, danger. Sizes: sm, md, lg. States: default, hover, pressed, focus-visible, disabled, loading.
- Every interactive component ships with an accessible name, visible focus, keyboard operation, reduced-motion behavior, and both themes. Features do not reimplement these locally.
- A scrollbar stays quiet: thin, no arrows, no track of its own colour, and a thumb only a little stronger than a hairline. It is painted only while the pointer is inside the pane it scrolls, since a bar that is always there is furniture and sits over the words of a narrow pane; only its paint is gated, so the room it takes never changes and nothing in the pane slides when a hand arrives or leaves (`src/styles/tailwind.css`). A screen with nothing to hover — a phone, a remote desktop with no mouse — keeps the thumb, because there the bar is the only thing that says what is off screen.
- Dropdowns, selects, and menus: the trigger shows the current selection, Escape closes, arrows and typing work, short lists stay inline and long ones become searchable, and the list aligns to the trigger without leaving the viewport. The chosen item is semibold on the selected fill, not marked with a circle or a tick that leaves the row looking unanswered. The caret sits inside the trigger's own box, and one control (`ui/page/Field.tsx`) serves every choice in the app — a page does not reach for the browser's `<select>`. A menu scrolls once, in its own surface: a list inside it that caps its own height makes a second scroller beside the first, and a column of a fixed height shrinks the rows it holds down to their minimum height, so their words fall outside the row's own fill. A scroller is also the box that what it scrolls belongs to: a column with its own scroll is `relative`, or a thing placed absolutely inside it — a field's hidden hint, say — keeps the page as its containing block, stands where its place in the scrolled content falls outside the window, and gives the whole screen a second scrollbar beside the column's own. A column that scrolls reaches the edge of the window it is read in, rather than stopping short above a band of the page's own padding (`ui/page/List.tsx`). A choice whose value already says what it is — a model's name, a reasoning level — shows the value alone, with its label kept as the accessible name and as the head of the list it opens; a label is for a value that could be anything.
- A control is given its state by the caller, not worked out inside a tooltip: a tooltip's trigger folds a function `className` into text, which leaves the row it wraps with its link and no shape.
- Keep components presentational. Data and feature logic live outside; components take values in and report intent out.
- Feature-local components stay in the feature directory and move into ``web/src/ui/`` only after a second real use. Describe each shared component in a doc comment at the top of its file, with one example of correct usage, and list its folder in the layout of `web/README.md`.
- Changing a shared component updates every call site in the same change, or adds a variant and deprecates the old one instead of breaking consumers.

## Interaction
- Respond immediately. Use optimistic updates when failure can be handled safely.
- Prefer Undo, and only when the action is actually reversible. Confirm only significant, irreversible actions.
- Reveal gradually: a glance, a closer look, a detailed view.
- A control that carries what is on screen somewhere else — Copy — waits for the block it belongs to be hovered or focused (`copy-quiet` and `reveal-copy` in `web/src/styles/tailwind.css`). The words are the content; a quiet button beside every message, tool call and code block at once is noise. A screen with nothing to hover keeps the control in place.
- A state is said once, by the thing that owns it: a chat that ended carries the word in its own tag, so the line under the composer adds nothing — and the button that goes on from it is labelled for what it now does (Continue), because the state and the action are two different things a person asks where they are; a count is not repeated by a sentence under the heading that counts it, the day a report was read on is said by the list that chose it rather than again in the title of every card on it, and the number at the end of a row that already names what it counts is a number — "Chat 2", not "Chat 2 new".
- An agent's message keeps the newlines it was written with, because a selection copies what is drawn: a break drawn as a space is gone from anything pasted out of the screen, and a transcript pasted into a field arrives as one line. A Markdown file is the other kind of writing — hard-wrapped by whoever wrote it — so there a newline stays soft and only a blank line makes a paragraph.
- The field that writes to an agent names the agent — "Write to Moebius" — which is why no pill beside it repeats the name; a sheet floating over another page says which page it is looking at, in a line under its own name, because the page being asked about is the one half-covered behind it. The conversation started in that sheet is a chat of the Chat page like any other — the sheet is a window onto it, not a second kind of chat — so it is listed there and unread until it is read somewhere: reading it in the sheet marks it read, minimising the sheet does not, and an answer that arrived while it was closed is still waiting.
- The package sheet (`web/src/packages/`) is the second sheet floating over the pages, made of the same pieces as the floating chat (`ui/page/Sheet.tsx`: Escape or the minimise control hides it, the focus returns to the button that opened it, and its state — the search, the tab, the package being read — waits where it was left). It is pointed at one catalog at a time: the Plugins page's "Browse packages" opens it on the Moebius registries (plugins, workflows, rules, skills) and the Extensions of an agent's editor opens it on pi.dev, for that agent. Opening it from the other place switches the catalog. It shares one slot at the right of the window with the floating chat (`ui/page/SheetSlot.tsx`): opening either minimises the other, which keeps its state, Escape reaches only the sheet that is showing, and the round buttons stay in a row under the slot so none is hidden by a sheet. Below 1536px (`2xl`) the sheet lies over the page, which keeps its width, since an editor squeezed beside a sheet is worse than one that is covered until the sheet is minimised; from 1536px the page leaves it its room (`2xl:pr-` on the shell's page), so the editor is not under it. The search field has the focus when the sheet opens. It has two tabs, Browse (a search field that waits for the typing to settle, a kind filter, results with name, kind, version, description, "Installed 1.0.0" and "Update to 1.1.0", downloads for Pi packages) and Installed (Update, Remove, and Update all for Pi). A package opens in place of the list, with a way back that names where it came from. What an action did is said in the sheet by a notice in the API's own words and never as a broken page: `Installed <name> <version>.`, the plugin's own error when it does not run, "Restart the server for it to take effect.", a registry that could not be read beside the results of the others, a refusal with its sentence, and for a session that is not a person's, whose it is not. A plugin installs at once, so removing one asks first; a workflow, rules or skills package and every Pi package is a change a person merges, so the sheet says so before the press, never asks twice, and after it links to that change in the Inbox (`/inbox?change=<id>`, the Inbox narrowed to it), minimising itself for the page it leads to. The `package_*` events and `extension_update_available` (the nightly check of the Pi packages, whose item is in the Inbox) read it, and the Plugins page's list of installed packages, again. A workflow, rules or skills package is removed only as a proposal, so it is said as `Proposed removing <name>.` with the link to the change and is not asked about first; a plugin goes at once, so it is asked about once.
- A control that cannot be used and has a reason carries it where a mouse, a keyboard and a screen reader all reach it, never as a line of text beside it and never in the browser's own tooltip box. A `title` draws a strip of somebody else's design system over the page it sits on, in colours and a font and a delay nobody chose, and a disabled `<button>` is out of the tab order, so neither it nor its `title` reaches a keyboard. `ui/components/Button.tsx` therefore keeps such a button focusable (`aria-disabled`, every click ignored), shows the reason in the app's own tooltip on hover and on focus, and keeps it for a screen reader in `aria-describedby`. A control that simply has nothing to do is disabled and says nothing — Save with nothing waiting is that control. Where it would change nothing whatever it did, it is not offered at all: a chat window already showing a conversation nobody has started offers no way out of one. Keep errors beside the affected content, with a useful next step.
- Empty states say what belongs there and how to begin, unless the next step is already obvious. One is a card only where it stands on the page itself; on a surface that is already one — a lane of the board, a sheet, a panel — it is `plain` (`ui/page/Empty.tsx`), because a second surface under the same sentence reads as a card that has lost its words. Its heading names the place, so a place already named on screen — a column under its own header — is the sentence alone, and a state that is the whole of an empty place is centred in it rather than left at its top.
- Loading placeholders match the expected layout; keep existing content during refreshes. Only the first read gets one (`ui/page/Skeleton.tsx`): rows where the list of rows will be, lanes where the board's lanes will be, lines where a file's lines will be, so the page fills in place instead of moving under the eyes. The bars carry no words of their own — a sentence about to be replaced by a different sentence is a promise nothing can keep — and they are filled with the hairline token, the tint a divider is drawn with, so a bar reads as a line not drawn yet rather than as a control that cannot be used. What the spinner used to say out loud is still said: the placeholder is a status region whose sentence is spoken rather than shown, which is also why a spinner stays where there is no layout to mirror and real work is happening — the app reaching a server for the first time, an agent's turn still being written.
- A card has one ⋯ menu for what a person does to it besides deciding (`app/board/CardMenu.tsx`): Block… or Unblock, and Delete…. It stands beside the title of the card on the board and beside the close control of the dock, is a button with an accessible name ("More actions for #12"), opens with Enter or Space and closes with Escape, and keeps every key and click to itself, because the card it sits in opens on Enter, is picked up on Space and the dock closes on Escape. A choice that needs words opens a dialog of the page (`CardDialogs.tsx`): Block… asks for a reason and says it is optional; Delete… asks once, says what goes and, for a card of a forge, that the issue stays open there and is not made a card again, and its button is the danger one with its own label ("Delete card"). A refusal stays in the dialog beside the buttons.
- Blocked and waiting are two states with two words. A card a person or the Moebius agent blocked carries the tag "Blocked", in the error tone, and the reason in its tooltip and in the dock ("Blocked" row); a card that depends on other issues says "Waiting on #12", in the attention tone. The dock keeps the two apart in its rows: "Why it waits" is the reason the card's script gave, and "Waiting on" lists the issues it depends on. A blocked card is never the next one to start, and a drop on a column says to unblock it first. A card that was deleted takes its dock with it: the dock closes rather than opening another card.
- Preserve navigation, drafts, selections, and reading position.
- A long conversation opens at its last message and is read backwards a page at a time (`chat/useThread.ts`): draining a run's whole log before its first line appeared left a page showing nothing for a second or two, and nobody scrolls up to a message until they decide to. What is above the window is fetched when a person reaches the top of the list — the gesture that asks for it — and it is added without moving the turn being read, because a page of history that shoves the sentence in front of them off the screen is not a page they asked for. Nothing is offered for that scroll: a row above the oldest turn that waits to be pressed repeats a gesture the person has already made, and one that promises the rest of a chat which has none is worse. It appears only while the page above is on its way, drawing the turns coming, or after it failed, with the reason and the way to ask again. Reaching the top is the only way to read older messages, so a first read that stops at its page limit with too little content to scroll leaves nothing that asks for more; that is a known gap, not handled yet.
- Interrupt only for failures, blockers, decisions, and meaningful completion. Say what happened, what the system did, and whether action is needed; open the relevant place when a notification is selected; never repeat what is already on screen.
- Keyboard: visible focus, logical order, predictable shortcuts. Escape closes overlays. Background updates never move, remove, or replace what someone is using.

## Motion and imagery
- Update content in place. Never scroll someone away from what they are reading; follow newly arriving content only when they are already at the end. A step someone opens is read where it is: unfolding one lets go of the end, even when the list was sitting on it. Do not animate the same content twice.
- About 180ms ease-out for routine transitions. Springs sparingly. One restrained moment at completion.
- Activity indicators stay subtle and carry real status text. Respect reduced-motion preferences.
- One icon family, consistent stroke weight, 16px inline and 20px in controls. Service logos only to identify that service. No decorative symbols that imply intelligence without explaining it.
- Meaningful images get useful alternative text and room enough to inspect.
- Skip decorative gradients and glows, progress without context, unsupported time estimates, unnecessary celebration, and redundant success messages.
